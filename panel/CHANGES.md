# PRISMA admin — изменения

## Пятая сессия: баги и недоработки (Приоритет 2)

- **Новый раздел «Репорты»** (`/dashboard/reports`) — жалобы из бота
  (`reports`) наконец видны в админке: тип, описание, кто подал, когда.
  Фильтр открытые/решённые/все, кнопка переключения статуса
  (`reports.status`, новая колонка — см. миграцию в архиве бота).
- **Кнопки «Снять варн» / «Снять мут»** на каждой записи в истории
  модерации (`ModerationPanel.tsx`), не только через общий селектор
  действий. Новый эндпоинт `POST /api/moderation/logs/[logId]`:
  - для `WARN` — помечает запись `revoked` (soft-delete, история не
    теряется);
  - для `MUTE` — снимает `users.is_muted`/`muted_until` и добавляет новую
    запись `UNMUTE`, а не редактирует исходный `MUTE` (честная история:
    видно и когда замутили, и когда сняли, отдельными строками).
  Игрок получает уведомление в Telegram при снятии.
- **Рейтинг теперь пересчитывается** при каждом действии модерации
  (issue и revoke) — `lib/rating.ts`, формула зеркалит
  `bot/activity.ts` на стороне бота (два независимых деплоя, общего
  пакета между ними нет, поэтому формула продублирована — держите их в
  синхроне, если будете её менять).

## Предыдущие сессии

## Вход по email вместо Telegram Login Widget

Полностью убран Telegram Login Widget (`TelegramLoginButton.tsx`,
`lib/telegram-verify.ts`, `/api/auth/telegram`). Вместо него —
`EmailLoginForm.tsx` на странице входа, с двумя режимами:

- **Ссылка на email (magic link)** — `POST /api/auth/magic-link` вызывает
  `supabase.auth.signInWithOtp(...)`, письмо реально отправляется через
  почтовый провайдер, настроенный в вашем Supabase-проекте. Ссылка ведёт на
  `/auth/callback`, который завершает вход и **только затем** проверяет
  allow-лист.
- **Пароль** — `POST /api/auth/login` вызывает
  `supabase.auth.signInWithPassword(...)`. Пароль администратор задаёт себе
  сам после первого входа по ссылке — блок «Аккаунт» на странице «Ещё»
  (`AccountSettings.tsx` → `POST /api/auth/set-password`). Изначально ни у
  кого пароля нет, только через Supabase Dashboard или через первый вход по
  magic link + установку пароля.

**Allow-лист администраторов** (`lib/admin-emails.ts`) проверяется в двух
местах:

1. `/auth/callback` — сразу после входа по ссылке; если email не в списке,
   сессия сразу завершается (`signOut`) и человек попадает обратно на `/`
   с `?error=not_an_admin`.
2. `proxy.ts` — на **каждый** запрос к `/dashboard/*`, даже если сессия уже
   существует. Это защита на случай, если email убрали из списка уже после
   того, как у человека была активная сессия — доступ теряется мгновенно,
   без необходимости отзывать сессию отдельно.

Источники allow-листа — оба варианта работают одновременно:

- переменная окружения `ADMIN_EMAILS` (через запятую);
- таблица `admin_emails` (миграция `supabase/migrations/0001_admin_emails.sql`) — удобна, если список меняется чаще, чем деплой.

`POST /api/auth/magic-link` намеренно **не** проверяет allow-лист перед
отправкой письма — иначе по ответу можно было бы угадывать, чей email
входит в список администраторов. Реальная граница доступа — на callback и
на proxy.

**Важно:** `.env.local` в этом архиве содержит настоящие ключи Supabase
(`SUPABASE_SERVICE_ROLE_KEY` и т.п.) и раньше содержал `BOT_TOKEN` — эти
секреты стоит считать скомпрометированными, если архив куда-то
пересылался, и по-хорошему их стоит перевыпустить в Supabase Dashboard.
`BOT_TOKEN`/`NEXT_PUBLIC_BOT_USERNAME`/`ADMIN_TELEGRAM_IDS` из `.env.local`
убраны — админке они больше не нужны (бот использует свой собственный
`BOT_TOKEN` в своём окружении, это не то же самое значение, что нужно
переиспользовать здесь).
