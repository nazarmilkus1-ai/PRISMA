# PRISMA Minecraft-плагин — изменения

## Приоритет 2: баги и недоработки

### Главный фикс: `/unmute` (и `BAN`/`UNMUTE` вообще) не доходили до сервера

`ModerationPollTask.java` опрашивал `moderation_logs` с фильтром
`type=in.(KICK,MUTE)&source=eq.DASHBOARD`. Из-за этого:

- `BAN` и `UNMUTE` не обрабатывались вообще, для любого источника;
- всё, выданное из Telegram-группы (`/warn`, `/mute`, `/kick`, `/ban`,
  `/unmute` — они пишут `source='BOT'`), плагин просто не видел.

Строка запроса теперь `type=in.(WARN,KICK,MUTE,BAN,UNMUTE)`, без фильтра
по `source` — обрабатываются все типы из обоих источников. `WARN`
подтверждается сразу (`applied_at` проставляется), так как у него нет
игрового эффекта — это чисто Telegram/панельная запись.

### `UNMUTE` теперь реально снимает мут у онлайн-игрока

`PlayerStateCache` раньше умел только `setMuted(...)` — снять мут можно
было только истечением времени. Добавлен `unmute(UUID)`, вызывается из
`ModerationPollTask` при обработке типа `UNMUTE`.

### Активность за игру на сервере

`JoinQuitListener.onJoin` теперь при каждом входе:

1. пишет строку в новую таблицу `activity_events` (`source='MC_SESSION'`,
   см. миграцию `../telegram-bot/migrations/0003_activity_rating_and_revocations.sql`
   в архиве бота — таблица общая для бота и плагина);
2. инкрементирует `users.activity_score` (read-modify-write через
   PostgREST — не атомарно, но конкуренция здесь минимальна и потеря
   одного начисления при одновременном входе двух игроков не критична).

Не пересчитывает `users.rating` тут же — см. «Известные ограничения» в
CHANGES.md бота.

## Не затронуто в этой сессии

Whitelist, чат-логи, кланы, IP-баны/муты (из предыдущей сессии) — без
изменений. Полный обзор UI/бизнес-логики плагина не проводился, только
точечные фиксы из списка Приоритета 2.
